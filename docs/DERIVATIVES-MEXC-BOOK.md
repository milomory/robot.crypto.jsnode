# MEXC: snapshot + непрерывные обновления BTC/ETH

1 октября 2026. Реализовано восстановление проверяемых **50 уровней на каждой
стороне** perpetual-книги. Это не заявление о полноте всей глубины биржи, наличии
арбитража или готовности реального исполнения. **Сетевая приёмка BTC и ETH прошла**, каждый архив независимо воспроизведён.
Synthetic tests и фактические публичные архивы обозначены отдельно.

## Как устроена проверка

1. Свежая спецификация одного инструмента задаёт contract size, price tick и lot.
   После неё открывается одна публичная WS-подписка на тот же BTC или ETH.
2. Обработчик WS установлен до подписки. После acknowledgement выполняется один
   REST `depth/<symbol>?limit=1000`; WS-дельты всё это время сохраняются в буфере.
3. Snapshot содержит version V. Покрытые им buffered versions ≤V пропускаются;
   первая применённая обязана быть V+1. Все увиденные версии, включая пропущенные,
   идут непрерывно. Gap/duplicate/reorder завершают экземпляр без recovery.
4. Количество в delta абсолютное: оно заменяет прежнее, ноль удаляет уровень.
   Обе стороны применяются атомарно перед проверкой пересечения bid/ask.
5. Только состояние после непрерывного обновления с matching-engine `cts`
   получает проверенное время. Возраст повторно проверяется при финальной оценке,
   чтобы ожидание REST не сделало старый буфер «свежим».

Цены, версии и количества сохраняются точно. Объём base = contracts × size;
Number не используется для арифметики сумм. Цена/количество проходят tick/lot
валидацию исходной спецификации этого же capture.

## Граница известной глубины

Начальный snapshot фиксирует неизменяемые `bidFloor` и `askCeiling` — самые
глубокие полученные цены. Дальнейшие редкие обновления за этими границами не
доказывают полноту промежутка и не расширяют его.

Поддерживаются все известные уровни внутри границ, максимум 10 000 на сторону.
Для результата нужны не менее 50 положительных уровней на каждой стороне.
Удаление глубокого уровня допустимо, пока этого достаточно. Если уровень 50
пришлось бы взять из неизвестной области, сбор останавливается, даже если оттуда
пришли отдельные обновления. Crossed/locked книга отвергается.

Выход: `verifiedDepth=50`, `entireBookKnown=false`, `executable=false`.
Freshness означает соблюдение выбранного окна времени, а не гарантию исполнения
по этой цене. Локальный clock skew всё ещё влияет на эту проверку.

## Одноразовый сетевой профиль

На один явно выбранный BTC или ETH:

- максимум **2 GET**, одно WS-соединение и одна подписка;
- metadata ≤5 с, bootstrap ≤3 с, WS ≤20 с от зафиксированного начала, весь capture ≤25 с;
- ≤256 WS frames, ≤512 KiB на HTTP response/frame, суммарно ≤4 MiB исходных данных;
- один public ping через 10 с после open; никаких auth/private channels;
- завершение после ≥10 применённых обновлений: буфер при bootstrap применяется
  атомарно, поэтому в редком случае итоговое число может быть больше 10;
- первый отказ HTTP/API, TLS/transport, schema/version, времени или глубины
  останавливает весь capture. Нет retries/reconnect/fallback/добавочных snapshots.

Поздний ответ REST после остановки не изменяет уже закрытый результат; reader
и запрос отменяются. Предел принятия WS frames проверяется после их сборки native
WebSocket и не является лимитом памяти самого сетевого декодера. Сроки не обещают
жёсткое время обработки OS scheduler/close handshake.

```bash
# Каждый запуск отдельный и ограниченный. После отказа новый не стартует сам:
npm run lab:mexc-book -- capture BTC /tmp/NEW_BTC_DIRECTORY
npm run lab:mexc-book -- capture ETH /tmp/NEW_ETH_DIRECTORY

# Только offline:
npm run lab:mexc-book -- replay /tmp/EXISTING_DIRECTORY
```

Первое принятие проверяет BTC, затем ETH только после успешного BTC. Это не D1
расписание. Runtime Crypto/Spot observer/scan/live-lock и средства не меняются.

## Детерминированный архив

`MexcBookSession` обрабатывает упорядоченные frame/bootstrap events. Archive
содержит raw metadata, bootstrap, WS frames и нормализованные результаты, точное
начало WS-этапа и порядок получения. Присоединять прежние независимые metadata
или дельты как свежие нельзя.

Replay заново парсит raw и повторяет merge, проверяет endpoint/market, receipts,
пределы и каждый производный результат, включая финальные top50/base amounts и
source age. SHA/canonical JSON защищают внутреннюю целостность, не доказывают
криптографическую подлинность ответа биржи или актуальность исторического снимка.
Непринятый произвольный error payload не сохраняется: ошибка — закрытый код,
replay доказывает принятый префикс, а не причину несохранённого ответа.

Архив ограничен 128 MiB отдельно от 4 MiB raw: до 256 дельт могут разрастись при
добавлении нормализованных полей. Каталог 0700, файлы 0600/exclusive/fsync;
частичный архив сохраняется до проверки. Успешный replay неполного capture не
означает успешность сетевого сбора.

[WS depth и cts](https://www.mexc.com/api-docs/futures/websocket-api/order-book-depth),

WS-first buffering — наша реализация защиты от гонки snapshot/subscription;
непрерывность подтверждается версиями каждого сообщения, а не одним флагом compress.

Далее: совместить восстановленные perpetual books с OKX и Spot на проверяемом
общем времени; определить пригодные timestamps остальных метрик и пересчитать
сетевой/дисковый бюджет D1. Затем отдельный протокол сбора возможностей и проверка
чистого результата на новых данных. [Общий план D0–D5](DERIVATIVES-OPPORTUNITY-PLAN.md).


## Фактическая приёмка

| Capture | GET / WS | Bootstrap на сторону | WS frames / применено | Весь capture | Возраст итогового cts |
| --- | --- | --- | --- | --- | --- |
| BTC | 2 / 1 | 1 000 | 88 / 52 | 1 727 мс | 770 мс |
| ETH | 2 / 1 | 1 000 | 11 / 10 | 2 908 мс | 169 мс |

BTC применил 52 дельты сразу при присоединении buffered snapshot, поэтому
ограничение «не менее 10» не подменяется утверждением «ровно 10». Это также
проверяет реальную гонку REST/WS; предыдущие покрытые версии пропущены без разрыва.
Known levels на выходе: BTC bids/asks 1001/1002, ETH 1000/1000; проверяемые top50
остались внутри неизменённых границ. Оба результата `executable=false`.

Public fixtures и manifest:

- `fixtures/market-data/mexc-book-btc-public-20261001.json`, 280 696 байт,
  SHA `f50369b8af1941d2faf6e7d4b89c1612a7dd305bf1f2fadc377def8b813d8a48`.
- `fixtures/market-data/mexc-book-eth-public-20261001.json`, 219 502 байт,
  SHA `3091f508d803e416a216890d9aa771a74148311f4f2276ccb5ed8ebced4ed64a`.

Compiled capture и replay обоих архивов PASS. Всего четыре GET/два соединения;
повторных попыток, account requests и production deploy не было. Эти времена —
два коротких наблюдения, не обещание будущей задержки и не доказательство прибыли.


Независимая приёмка дополнительно восстановила обе книги собственными Map напрямую
из raw (в обход production-класса) и получила те же top50. В BTC финальный source
age 770 мс включает 624 мс между последним frame receipt и оценкой после обработки
буфера; для ETH это 169 и 11 мс. Называть source age чистой сетевой задержкой нельзя.


Проверки: **4 910 PASS**, 15 прежних PostgreSQL skips; API/UI build и строгие типы
market-data PASS. Полный прогон использовал `--maxWorkers=2`: исходный параллельный
прогон дал один 5-секундный timeout старого study-теста; его отдельный повтор и
полный повтор прошли без изменения ожиданий/таймаутов. Один прерванный SIGTERM
запуск не засчитан. Добавлено 336 тестов; [validation](evidence/mexc-book-20261001/validation.json),
[фактическая приёмка](evidence/mexc-book-20261001/acceptance.json).
