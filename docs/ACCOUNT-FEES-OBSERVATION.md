1 октября 2026. Продолжение [подготовки по остаткам и резервам](ACCOUNT-FUNDS-PREPARATION.md).
Новый вариант журнала получает ставки только из проверенного приватного архива.
Ручных полей maker/taker в его команде подготовки заявки нет.

[Приёмка на Hyperion](evidence/account-fees-20261001/README.md) пройдена:
пять реальных GET, независимая проверка архива и неизменность основного робота.
Установлен только отдельный сборщик; новый журнал подготовки остаётся локальным.
3 267 тестов и 41 ops-проверка прошли, 15 прежних PostgreSQL-проверок пропущены.

## Что читается

| Биржа | Точный порядок GET | Результат |
| --- | --- | --- |
| MEXC | `/api/v3/uid`, `/api/v3/tradeFee?symbol=BTCUSDT`, `/api/v3/mxDeduct/enable` | UID, персональные maker/taker и текущее состояние оплаты MX |
| OKX | `/api/v5/account/config`, `/api/v5/account/trade-fee?instType=SPOT&instId=BTC-USDT` | UID/main UID/type, feeType, единственная применимая группа maker/taker |

Всего пять запросов, без повторов и перенаправлений. Неверная версия credentials
блокируется до сети, неверный UID — до чтения его тарифов. Credentials неизменяемы
внутри вызова. Старые четыре GET остатков и их установленный артефакт не расширены.
Снимки комиссии и остатков последовательно собираются отдельно; атомарное состояние
всей биржи или контроль ручных действий владельца не заявляются.

Новый изолированный transport сохраняет исходные цифры JSON, включая `0E-18`,
без преобразования тарифа через float. Числовой UID не превращается в строковый;
duplicate keys, неподходящая пара/группа, неверная кодировка и форма ответа отвергаются.
Чтение ограничено 30 секундами. При подготовке каждый архив не старше 60 секунд
от начала своего сбора; обратный ход времени блокирует операцию. Для тарифного
response timestamp старше запроса более чем на 60 секунд есть отдельный blocker.
Это правило не переносится на `uTime` баланса, которое может означать последнее изменение.

Ставки MEXC читаются из [Query Symbol Commission](https://www.mexc.com/api-docs/spot-v3/spot-account-trade/query-symbol-commission).
Настройка MX — отдельный [read-only endpoint](https://www.mexc.com/api-docs/spot-v3/spot-account-trade/query-mx-deduct-status).
У OKX используется [применимая группа Get fee rates](https://my.okx.com/docs-v5/en/#trading-account-rest-api-get-fee-rates).
Обновление settings, перевод, покупка MX, ордер и отмена в transport отсутствуют.

## Привязка и происхождение

`account-fees-runtime.ts` использует существующий private pin и прежнюю selection
из `/home/mil/crypto-account-funds/binding` только для чтения. Его HMAC связывает
выбранные аккаунты и прежнюю credential bundle. Новый сборщик не меняет enrollment,
`pin.sourceHash`, ключ HMAC или принятый старый источник `da4ad8a2…`.

Приватный архив содержит два разных хеша: `bindingSourceHash` принятого прежнего
источника и `collectorSourceHash` нового артефакта. Верификатор проверяет оба,
receipt/SHA, HMAC pin, selection receipt, UID и времена каждого из пяти запросов.
Collector hash отдельно закреплён в manifest нового журнала. Надпись «verified»
в пользовательском JSON не создаёт доказательство: проекция неизменяема и имеет
проверяемое происхождение внутри модуля. Старые поля assessment не заменяют проверки.

Receipt/pin должны поступать из принятой защищённой границы. SHA и HMAC pin
не являются подписью ответа биржи; доверенный файловый владелец остаётся частью
контракта. Проверка credentials относится к моменту capture, не к любому будущему
вызову. Приватные UID, суммы, raw rates и ключи не печатаются в публичном receipt.

## Как используются ставки

- Для обычного limit берётся большая расходная ставка maker/taker. Rebate OKX
  не считается будущими деньгами и не уменьшает резерв: его вклад в расход нулевой.
- [OKX feeType](https://my.okx.com/docs-v5/en/#trading-account-rest-api-get-account-configuration)
  задаёт модель валюты: `0` — получаемая валюта, `1` — quote. Это проверенная
  настройка, а не доказательство фактического списания будущего fill.
- У MEXC подтверждается персональная ставка, но toggle MX сам по себе не доказывает
  скидку 20% или валюту будущего списания. При неизвестной валюте расчёт допуска
  остаётся закрытым. Настройки MX не изменяются.
- Полный fee cap резервируется вместе с principal; cap ниже оценки блокирует
  подготовку. При обновлении тарифов перепроверяются и прежние локальные intents:
  выросшая комиссия не проходит через старый маленький резерв. Он остаётся в
  журнале до явного локального release, деньги не «освобождаются» автоматически.

`rateProvenanceVerified`/`feeProvenanceVerified` теперь могут быть true для принятой
связки архивов. `feeCurrencyPolicyVerified` отдельно описывает известную настройку.
`feeCurrencyVerified`, `fillRoundingVerified`, `liveAllowed`, `executable` остаются
false: округление вверх до 18 знаков — модель, не доказанное округление каждого
частичного исполнения. Все деньги не становятся доступными из-за успешного чтения ставки.

Остаются консервативные ограничения предыдущей денежной модели: buy fee в BTC
требует соответствующего native cap из имеющихся средств, хотя удержание из
получаемого BTC требует отдельного gross/net контракта; USDT-комиссия limit sell
не имеет доказанной верхней границы выручки. Начальная себестоимость BTC, семантика
MEXC spendable/main account и nullable обязательства OKX не исправляются этим этапом.

## Журнал с обязательным тарифным архивом

`schema: 2`, `kind: fee-bound-account-funds-preparation-journal` создаётся отдельной
командой. Импорт сохраняет архивы остатков и тарифов одной CAS-записью. Оба должны
иметь одинаковые pin/bundle и выбранные аккаунты. Replay воспроизводит решение
на историческое время; новый stage заново проверяет свежесть обоих архивов.
Старые команды schema 1 отвергают schema 2; обратного fallback на декларацию нет.

Как и раньше, это локальная подготовка. В journal нет dispatch, exchange cancel
или sender. Физический корень/внешний checkpoint защищают последовательность в
указанном каталоге; второй каталог не считается общим production-бюджетом аккаунта.
Для размещения двух архивов размер записи теперь до 2 MiB, каталога 18 MiB;
committed budget по-прежнему 10 MiB, четыре ограниченных pending slots, 256 записей,
не более восьми импортов. Копирование/очистка журнала не является способом продления бюджета.

```text
npm run lab:account-funds -- init-bound JOURNAL KEY PIN LIMITS COLLECTOR
npm run lab:account-funds -- import-bound JOURNAL KEY FUNDS_ARCHIVE FUNDS_RECEIPT FEE_ARCHIVE FEE_RECEIPT PIN CHECKPOINT
npm run lab:account-funds -- stage-bound JOURNAL KEY INTENT CHECKPOINT
npm run lab:account-funds -- release-bound JOURNAL KEY RELEASE_JSON CHECKPOINT
npm run lab:account-funds -- inspect-bound JOURNAL KEY [MINIMUM_CHECKPOINT]
```

Все параметры после команды — пути. `COLLECTOR` — private JSON с единственным
`collectorSourceHash`; это проверенный release hash, а не ставка. `KEY` — путь к
внутреннему 32-byte binding key, не значение API key. Private owner/0600/обычный
одиночный файл, canonical compact JSON с необязательной новой строкой; raw pin и
архивы сохраняют свои исходные байты. `LIMITS=null` допустимо для создания пустого
журнала, но подготовка закрыта. User limits не выбираются из test fixtures.
В stdout только fixed status, checkpoint, counts и признаки; суммы/UID не выводятся.

Private operational acceptance is omitted from this review snapshot.

## Что после этого

Следующий технический шаг — принять применимость денежных полей и фактическую
валюту/округление комиссии на существующей непустой истории, затем единственный
серверный владелец лимитов и сверки после отправки. По-прежнему нужны выбранные
пользователем капитал/убыток/остаточный риск и подтверждение стратегии после издержек.
Новые ключи MEXC/OKX для этого этапа не нужны.
